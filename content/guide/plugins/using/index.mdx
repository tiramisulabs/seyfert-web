title: Plugins

Seyfert plugins are installable integrations composed by the client.

```ts
import { Client, definePlugins } from 'seyfert';
import { loggerPlugin } from './logger-plugin';
import { economyPlugin } from './economy-plugin';

const plugins = definePlugins(loggerPlugin(), economyPlugin());

const client = new Client({
    plugins,
});
```

Use a plugin when a package needs to add client helpers, context helpers, lifecycle work, commands, components, modals, events, middlewares, services, gateway behavior, autocomplete wrappers, or option fragments.

## The Shape

The public contract is intentionally small at the top level:

```ts
import { createPlugin } from 'seyfert';

export const plugin = createPlugin({
    name: 'example',
    imports: [],
    requires: [],
    client: {},
    ctx: {},
    options(current) {
        return {};
    },
    register(api) {},
    setup(client) {},
    teardown(client) {},
});
```

You usually do not need every field.

| Field | Purpose |
| --- | --- |
| `name` | Stable plugin identity used for ordering, diagnostics, and dependency checks |
| `imports` | Plugins this plugin brings with it; imports resolve before the importer |
| `requires` | Runtime requirements such as `plugin:storage`, required or optional |
| `client` | App-wide helpers exposed as `client.*` |
| `ctx` | Per-interaction helpers exposed as `ctx.*` |
| `options(current)` | Option fragments that need the current merged options |
| `register(api)` | Synchronous registration for commands, events, services, hooks, and options |
| `setup(client)` | Async startup after client helpers exist |
| `teardown(client)` | Cleanup through `client.close()` in reverse plugin order |

## Plugin, Adapter, Utility

Make the category obvious before publishing.

| Category | Use it for |
| --- | --- |
| Plugin | Behavior installed through `new Client({ plugins })` |
| Adapter | Replacing cache, REST, HTTP, gateway, storage, or another infrastructure interface |
| Utility | Functions, classes, decorators, or helpers users import manually |

A plugin can use adapters and utilities internally. They do not become plugins until the user installs an object through the `plugins` option.

## Real Packages

These packages are practical modern `createPlugin(...)` examples. They are more complete than the guide's introductory sample.

| Package | What to study |
| --- | --- |
| `@slipher/cooldown` | `createPlugin`, `client` and `ctx` helpers, command metadata, option fragments, decorators, and cache-backed behavior |
| `@slipher/scheduler` | lifecycle setup and teardown, `client.scheduler`, `ctx.scheduler`, decorators, driver abstraction, and optional persistent backends |
| `@slipher/logger` | context logger lifecycle, command/component/modal defaults, and setup-time logger installation |
| `@slipher/queues` | shared registry exposed on client and context, queue decorators, processors, producers, event hooks, and optional BullMQ backing |

The guide uses a smaller logger as the first walkthrough because these packages carry more production behavior than a beginner example needs.
